# ocr による全ファイル監査

`ocr scan` は差分ではなくファイル全体をレビューする。**PR 差分レビューが構造的に
見つけられない欠陥**——既にマージ済みで、しばらく誰も触っていないコードのバグ——を
探すための手段。

未設定なら先に `/ocr:setup` を実行すること。

## モデル

**`opencode-go` / `deepseek-v4-flash` を既定とする。** context 1M で大きいファイルにも
耐え、速く、コストも低い。

上位階層のモデル（`-pro` など）が常に良いとは限らない。context も出力上限も同じで、
世代が古ければ検出率で下回ることもある。切り替えるなら既知バグでの実測で判断する。

## 基本

```bash
# まず必ず preview。LLM を呼ばずに対象範囲だけ確認できる
ocr scan --preview

# 実行
ocr scan --provider opencode-go --model deepseek-v4-flash \
  --timeout 30 --concurrency 4 --format json > findings.json

# 生成物や fixture を除外
ocr scan --exclude '**/generated/*,**/testdata/*' \
  --provider opencode-go --model deepseek-v4-flash --timeout 30
```

モデル名は接頭辞なしで指定する（`opencode-go/...` 形式は opencode CLI の記法）。

## ⚠️ scan に `-B` は存在しない

背景コンテキストのフラグは `review` と `scan` で**揃っていない**。

| フラグ | `ocr review` | `ocr scan` |
|---|---|---|
| `-b, --background <文字列>` | あり | **あり（scan で使えるのはこちらだけ）** |
| `-B, --background-file <パス>` | あり | **なし** |

```bash
ocr scan -B AGENTS.md ...          # ✗ Error: unknown shorthand flag: 'B' in -B
ocr scan -b AGENTS.md ...          # ✗ 無言で通るが「AGENTS.md」の 9 文字しか渡らない
ocr scan -b "$(cat AGENTS.md)" ... # ○ 中身が渡る
```

**2 番目が最も危険。** エラーも警告も出ないため、背景を渡したつもりで何も渡っていない
状態のまま完走する。scan で背景を渡すときは**必ずコマンド置換で中身を展開する**。

また **`-b` には 8,000 文字の上限チェックがない**（`review` の `-B` にはある）。
超過しても黙って実行されるため、自分で確認すること。

```bash
wc -c AGENTS.md    # 8000 未満であること
```

## recall を上げる3つの運用

`ocr scan` の検出率は 1 回では高くない。効果の大きい順に:

**1. `--path` で小分けにする（最も効く）**

一度に渡すファイルを増やすと、1 ファイルあたりの掘り下げが浅くなり、見落としが増える。
**1 ファイル単独なら見つかるバグが、まとめてスキャンすると出てこない。**
回数を増やしても、その構成で見つからないバグは見つからない——範囲を狭める方が
検出できる上限そのものを上げる。

```bash
for d in src/db src/parser src/web; do
  ocr scan --path "$d" --provider opencode-go --model deepseek-v4-flash \
    --timeout 30 --format json > "findings-$(basename $d).json"
done
```

**2. 背景コンテキストとツール予算を併用する**

契約・記法・データ形式といったプロジェクト固有の不変条件に関わる欠陥は、
コードだけからは判断できない。scan には「この変更の意図」が存在しないので、
不変条件だけを渡す。

```bash
wc -c AGENTS.md    # 8000 未満を確認してから

ocr scan --path src/db -b "$(cat AGENTS.md)" --max-tools 100 \
  --provider opencode-go --model deepseek-v4-flash --timeout 30 --format json
```

**片方だけでは効かない。** 背景だけ与えると探索が深まった結果、既定のツール予算を
使い切って `failed` で終わる。「コードを読めば分かること」を削った簡潔な文書ほど
効果的で、網羅的な文書はノイズになり、探索が迷走してコストも跳ね上がる。

**3. 複数回まわして和を取る**

同じモデル・同じ対象でも、実行ごとに違う部分集合を報告する。
2 回目の上積みが最も大きく、3 回目以降は急速に減衰する。
4 回以上まわすくらいなら、同じ予算を `--path` の細分化に回す方がよい。

| 用途 | 回数 |
|---|---|
| 通常 | 1 回（範囲を絞る方を優先） |
| 重要な監査 | 2 回 |
| リリース前など見落としコストが高い場面 | 3 回 |

## ⚠️ タイムアウトの落とし穴

`--timeout` の既定は **1 タスクあたり 10 分**、`--concurrency` の既定は **8**。

**締切を超えたファイルは「指摘ゼロ + 警告」で返る。**
出力だけ見ると「このファイルはきれいだった」と全く区別がつかない。
これが最も危険な失敗モードで、監査したつもりで何も見ていない状態になる。

大きいファイル（目安として 1000 行超）は既定の 10 分に収まらないことがある。
さらに並行実行の競合でスループットが落ちるため、**ファイル数が多いほど超過しやすい**。
同じファイルが「単独なら通るが、全体スキャンでは落ちる」という挙動をする。

対処:

```bash
ocr scan --timeout 30 --concurrency 4
```

締切はクライアント側の設定値であってモデルの能力上限ではないので、上げれば通る。

## 結果の確認（必須手順）

**`status` と `warnings` を見るまで結果を信用しない。**

```bash
python3 - <<'PY'
import json
d = json.load(open('findings.json'))
print('status:', d['status'], '|', d.get('message', ''))
print('summary:', d['summary'])
for w in (d.get('warnings') or []):
    print('!! レビュー未実行:', w['file'], '-', w['message'])
rank = {'high': 0, 'medium': 1, 'low': 2}
for c in sorted(d.get('comments') or [], key=lambda c: rank.get(c.get('severity'), 3)):
    print(f"[{c.get('severity')}/{c.get('category')}] {c['path']}:{c.get('start_line')}")
    print('   ', c['content'][:200].replace('\n', ' '))
PY
```

`status` が `completed_with_errors` なら、**警告に出たファイルだけ**を
より長い `--timeout` と低い `--concurrency` で再実行する。

```bash
ocr scan --path <警告に出たファイル> \
  --provider opencode-go --model deepseek-v4-flash \
  --timeout 30 --concurrency 2 --format json
```

`status` が `failed` の場合、`comments` は `null` になる（空配列ではない）。
`--max-tools` を上げて再実行する。

全ファイルが実際にレビューされるまで「問題なし」と報告してはいけない。

中断した場合はセッション ID で再開できる。

```bash
ocr scan --resume <session-id>
```

## 指摘の検証

指摘はモデルの出力であって事実ではない。修正に着手する前に:

1. 指摘された行を実ファイルで読む。行番号がずれていたり、存在しないコードの話をしていることがある
2. 到達可能性を追う。呼び出し側が保証している不変条件や、プロジェクトの規約文書に反する指摘は偽陽性
3. セキュリティ系はシンクまで経路を追う。エスケープ漏れは、描画側がエスケープしていなければ初めて脆弱性になる
4. **重大度も再現回数も正しさの根拠にならない。** 複数ランで毎回 high と判定された指摘が、
   実際に動かすと完全な誤りだったという例は珍しくない。逆に本物のバグが数回に1回しか
   出ないこともある。集約は「候補を漏らさない」ためであって、「正しさを投票で決める」
   ためではない。最後は必ずコードと実行で確かめる
5. 修正には「バグが存在したことを示す回帰テスト」を添える

**明白な修正が別のものを壊す指摘**に特に注意する。ガード条件が意図的にそう書かれている
ことは珍しくなく、周囲のコメントがその理由を説明していることが多い。
安全な修正が存在しないと判断したら、**修正しないことも正しい結論**。
その場合は再現手順と、なぜ直さないかの根拠を残す。

## 主なオプション

| オプション | 用途 |
|---|---|
| `--timeout <分>` | 1 タスクの締切（既定 10）。大きいファイルでは必ず上げる |
| `--concurrency <数>` | 同時スキャン数（既定 8）。下げると競合が減る |
| `--path` | 対象をディレクトリ／ファイルに限定（カンマ区切り）。分割すると recall が上がる |
| `-b, --background <文字列>` | 不変条件。**必ず `"$(cat file)"` で中身を渡す。`-B` は scan に存在しない** |
| `--max-tools <数>` | 1 ファイルあたりのツール呼び出し上限。背景を渡すなら必ず上げる |
| `--exclude` | gitignore 形式の除外パターン |
| `--preview` | LLM を呼ばずに対象だけ表示 |
| `--format json` | 機械可読出力 |
| `--model` / `--provider` | その実行だけ上書き |
| `--max-tokens-budget` | トークン上限。超えたら打ち切り |
| `--resume <id>` | 中断したスキャンの再開 |

## 位置づけ

段階を重ねると、それぞれ前段が構造的に拾えないものを拾える。

1. **決定論的** — linter、静的解析。無料・再現性あり・偽陽性ほぼゼロ
2. **`ocr review`** — プッシュ前の差分レビュー（→ `/ocr:review`）
3. **PR レビューボット** — 差分に対する第三者の目
4. **`ocr scan`** — 定期実行。差分が触れないコードを見る唯一の層

4 が重要なのは、PR ボットは**修正の差分**をレビューするのであって、
何ヶ月も前から埋まっている元のバグは見ないため。

なお 2 と 3 は取りこぼしが独立していることがある。同じ差分を一方が見逃し、
他方が捕捉する例は実際に起きるので、重複ではなく補完と考えてよい。
