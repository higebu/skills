# 委任から PR まで

メインは計画・振り分け・検収を担い、実装は子に任せる。テストやリントの
手順はここに書かない。各リポジトリの CLAUDE.md に従わせる。

`--finish` で呼ばれたら、自分が子である。手順 4 から始める。

## 1. 計画し、判断を前倒しする

- 作業を、完了条件を書ける単位に分ける。
- 実装中に人間の判断が要りそうな点を洗い出し、委任の前にユーザーへ聞く。
  聞いて決まれば、その作業は「前倒しできた」とする。
- 実装してみないと決まらない点が残る作業(探索的、設計が揺れている)は
  「前倒しできない」とする。規模の大小はここでは問わない。

## 2. 実行者を選ぶ

上から順に最初に当てはまるものを使う。

| 条件 | 実行者 |
|---|---|
| 前倒しできた | サブエージェント(Agent ツール) |
| 前倒しできない、かつ `HERDR_ENV=1` | herdr の新しいタブ |
| 前倒しできない、かつ `CLAUDE_CODE_REMOTE=true` | 別のクラウドセッション |
| どれでもない | サブエージェント。判断待ちで止まったら手順 3 で引き継ぐ |

長時間かかり、メインの文脈を食いそうな作業も「前倒しできない」と同じ扱いに
してよい。

### サブエージェント

- 設計判断を含む作業は `model: "opus"`、仕様が固まった機械的な作業は
  `model: "sonnet"`。
- 複数を並行させるときは `isolation: "worktree"` で作業ツリーを分ける。
- 子は人間と対話できない。判断が要る点に当たったら、推測で進めず止まって
  報告するよう指示に書く。

### herdr タブ

herdr スキル(`herdr --skill` で同梱版を表示できる。未導入なら
`npx skills add herdrdev/herdr --skill herdr -g`)を読み、その規則に従って
操作する。CLI の構文はインストール済みの `herdr` に確かめる。

herdr スキルの既定は「今のタブを分割し、同じ作業ディレクトリで動かす」だが、
このスキルでは次の構成をユーザーの指定として使う。同じ作業ツリーで並行して
編集すると衝突するため。

1. git で作業ツリーを分ける。置き場所はリポジトリの外にする。

   ```bash
   git worktree add -b <branch> ../<repo>-<branch-slug> <base>
   ```

2. 今のワークスペースに、その作業ツリーを開くタブを作る。返った JSON の
   `.result.root_pane.pane_id` をペイン ID として使う。予測しない。

   ```bash
   herdr tab create --cwd ../<repo>-<branch-slug> --label <branch-slug> --no-focus
   ```

3. そのペインで `herdr agent start <name> --kind claude --pane <id>` する。
4. 手順 3 の指示を `herdr agent prompt` で送る。
5. `herdr agent wait <name> --until blocked --until done --timeout <ms>` で待つ。
   `--timeout` は必ず付ける。
   - `blocked`: ユーザーに、そのタブを開いて答えるよう伝える。代わりに
     答えない。
   - `done`: `herdr agent read` で PR の URL と要約を受け取り、ユーザーに
     伝える。PR が出ていなければ、何で止まったかを読んで伝える。
   - タイムアウト: 再送せず `herdr agent read` で状態を確かめる。
6. タブと作業ツリーは PR がマージされるまで残す。片付けはユーザーに
   頼まれてから、`herdr tab close` と `git worktree remove` で行う。

### 別のクラウドセッション

- `create_session` に手順 3 の指示を `prompt` として渡し、`outcome_branch` に
  作業ブランチを指定する。`permission_mode` に `plan` は使わない。
- セッションのリンクをユーザーに伝える。判断が要る場面では、ユーザーが
  そのセッションを開いて直接答える。
- 子は終わってもメインに報告しない。`get_session` と `list_events` で
  様子を見て、成果物は PR で受け取る。
- クラウドのコンテナに herdr を入れて使わない。タブの画面がユーザーに
  見えず、herdr を使う意味がない。

## 3. 子への指示

子はメインの文脈を持たない。次をすべて書き、指示だけで作業が完結するように
する。

```
目的: <なぜ必要か。1〜2 文>
範囲: <触るもの / 触らないもの>
完了条件: <何がどうなれば終わりか。確かめられる形で>
判断が要りそうな点: <手順 1 で残ったもの。当たったら止まって聞く>
検証: リポジトリの CLAUDE.md にある検証をすべて実行する。
報告: 実行したコマンドとその結果、変更の要約、残った懸念。
```

herdr タブと別セッションの子には、末尾に次を加える。

```
仕上げ: 完了条件を満たしたら /dev-flow:ship --finish を実行し、PR まで出す。
最後の返答は PR の URL と 3 行以内の要約だけにする。
```

サブエージェントの子には「仕上げ」を書かない。手順 4 以降はメインが行う。

## 4. 検収

サブエージェントの差分はメインが、herdr タブと別セッションの子は自分の差分を
自分で検収する。「テストは通った」という報告をそのまま信じない。

- `git diff <base>...HEAD` を自分で読み、完了条件と範囲に照らす。
- 報告に実行したコマンドと結果がない、または差分が報告と食い違うときは、
  CLAUDE.md の速い検証を自分で走らせる。
- 足りなければ、何が足りないかを書いて子に差し戻す。

## 5. レビュー関門

1. `/code-review` を差分に対して実行する。
2. `/ocr-review` を実行する。
3. 指摘を仕分ける。
   - 実際に起こる経路を追えるものは直す。直したら 1 に戻る。
   - 起こる経路が無理筋なもの、直すコストが見合わないものは直さず、理由を
     控えておく。PR 本文の「意図」に回すか、ユーザーに伝える。
4. 新しい指摘が 0 件になったら抜ける。3 周しても収まらなければ止まり、
   残った指摘をユーザーに見せて判断を仰ぐ。

## 6. PR を出す

1. コミットメッセージは `/git:commit-message` に従い、
   `check-msg.sh --range <base>..HEAD` を通す。
2. 履歴を直すときは `/git:fold`、push は `/git:safe-push` を使う。
3. タイトルと本文は `/pr-description:write` で書く。
4. PR を作り、URL を返す。
